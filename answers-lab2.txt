(b) Why do user programs not read/write kernel memory? What specific mechanism enforces this?

User programs cannot access kernel memory because the kernel’s page tables mark its regions as not 
--user-accessible (the PTE_U flag is not set). 
This hardware-enforced permission prevents any code running in user mode from reading or writing into the 
--kernel’s memory space.
Thus, hardware-level paging permission bits protect the kernel from user-mode access.


(c) What is the maximum amount of physical memory that this OS can support? Why?

By default in JOS, the kernel remaps 256MB of physical memory (from physical address 0 up to 256MB) 
--starting at virtual address `KERNBASE` (0xf0000000). 
Hence, the OS is laid out to handle up to 256MB of physical RAM by direct mapping.  


(d) How much space overhead is there for managing memory at the maximum? How is this overhead broken down?

You need one 4 KB page directory with up to 1024 page tables at 4 KB each. 
That’s approximately 4 MB of space reserved just for the paging structures.


(e) When do we switch to EIP above KERNBASE, and why can we execute for a while at a low EIP even with paging on*?

After enabling paging, the boot code can still execute at a low EIP because the early page directory provides 
--an identity mapping for the first 4 MB. 
Once paging is on, the kernel then jumps to a high virtual address (above KERNBASE) where the kernel is linked,
-- and this dual mapping makes the transition seamless.
